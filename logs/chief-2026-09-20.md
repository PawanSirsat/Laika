**For the owner — `due_date` is an open product decision, not a defect.**

`update_task` shipped without `due_date`, and so did every other tool. I checked
this myself rather than taking CORE's word, and the result is **wider than they
reported**: `grep -rn 'dueDate\|due_date' server/src/` returns nothing at all —
not the schema, not a service, not a route. CORE only claimed it of
`schema.ts`. Tasks carry `started_at` and `completed_at`, which are **actuals,
not a plan**.

D-014 is the reason and says so in its title — *"The timeline is sprint-based;
tasks never get dates"* — with the cost spelled out: task dates imply
dependency-aware layout, a critical path, slip propagation, *"and a scheduling
model that has to be maintained forever."* Sprints were how the cheap version of
the Timeline got built instead.

So this is not something CORE missed and not something a reviewer should have
sent back. **It is a question the board has never answered:** the acceptance
criteria asked for `due_date` because the requesting agent wanted it, which is
the first real signal from a consuming agent that D-014's position may not
survive contact with how people actually use the board. Sprints have dates;
tasks do not; an agent importing 153 tasks wanted per-task dates and could not
have them.

**Nothing to do until the owner decides**, and deliberately no task filed for it
— filing one would presuppose the answer. If D-014 stands, §7.1's new prose
already records why, so the next reader stops asking. If it does not, it is a
schema change, a migration, a REST field, a client type and a UI affordance
before it is an MCP parameter, and it wants a decision entry before any of that.
