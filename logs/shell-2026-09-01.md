**Decisions**

  already on every `ProjectView`, so it costs no request and answers "where is

  Notes are right that the selection lives in the URL, and a stored fallback is
  the ambient selection under another name — two browsers would disagree about
  what a bare `/board` means.
- *`/members` asks rather than resolving.* AC2 permits either. A board with no

  project you did not pick is a permissions screen showing the wrong
  permissions. Flagged on the task for CHIEF to overrule if they disagree.
- *`orgLevel` marks the exceptions, carrying the project is the default.* The
  same inversion as `Route.public`: forgetting to mark a new route keeps the
  reader's context, which is harmless. The opposite default loses it silently,
  which is this defect.

## 01:05 +05:30 — LAI-424 the card hit area → review

**Changed**
- `server/web/src/routes/screens/board/board.css` — `.card` positioned and
  `cursor: pointer`, `.card:hover`, `.card-open::after` (the stretched hit
  area), `.card-above`.
- `server/web/src/routes/screens/board/TaskCard.tsx` — `card-above` on the
  elements carrying tooltips.
- `server/web/src/routes/screens/BoardScreen.tsx` — the open task reads from
  `?task=` instead of `useState`.
- `server/web/test/routes/screens/board/card-hit-area.test.ts` — **new**, 10
  tests, run red against the unmodified card first.

**Decisions**
- *Stretch the existing button, do not add a second handler.* The obvious fix —
  `onClick` on the `article` — gives assistive tech two ways in and fires twice
  for anyone using both. Stretching `button.card-key` with `::after { inset: 0 }`
  keeps one control, one Tab stop, one activation.
- *`cursor: pointer` on the design's authority, not mine.* The design file uses
  it 46 times and `grab` never. `grab` was ours: honest about dragging, silent
  about what people actually do. Dragging still works.
- *No shadow on hover.* I wrote `var(--shadow-lift, var(--shadow))` and removed
  it — there is no `--shadow-lift`, so the fallback would have resolved to the
  same shadow, a no-op dressed as a change, and inventing a token is not mine
  (D-020).
- *`?task=` done here rather than filed.* `setParam` already existed, so it was
  three lines.

**Discovered**
- *A test satisfied by its own explanation.* My cursor assertion matched a
  **comment** inside the `.card` rule reading "the design file uses
  `cursor:pointer` 46 times", so it stayed green when the declaration was
  mutated back to `grab`. I only found it because the mutation's red never
  arrived — the check CHIEF asked me to keep. `ruleFor` now strips comments
  before matching. **Any source-text assertion can be satisfied by prose about
  the thing instead of the thing.**
- *The CSS was right and the geometry was wrong.* I added
  `.card-key { position: relative }` for the focus ring; it made the key the
  containing block for its own overlay, so `inset: 0` sized the hit area back to
  the key — restoring the 3.6% while **every CSS assertion still passed**. Only
  `elementFromPoint` in a browser caught it.
- *AC3 described controls that do not exist.* The `+`, avatar and blocker are
  `<span>`s with tooltips and no handlers; the card's only interactive element
  was the key. Their real requirement is that the overlay must not swallow their
  **tooltips**. Said so on the task rather than inventing controls to satisfy the
  wording.
- *Playwright refusing to click was the proof.* It would not click `.card-title`
  because `button.card-open` "intercepts pointer events" — which is exactly the
  fix working. Clicking `article.card` succeeded, because the interceptor is a
  descendant.
- Filed **LAI-227**: no web test in this repo can click anything, because
  `node --test` cannot import a `.tsx`. Two p1 interaction defects in a row and
  528 passing tests said nothing about either. The task names the two candidate
  harnesses and points out that jsdom would have caught **neither** of today's
  mistakes, since it has no layout.

  panel open; Enter on the focused key → opens once; `+` → tooltip, no panel;
