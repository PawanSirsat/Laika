**Decisions**

- *Took `readyState`, not the option the task preferred.* The Notes favour
  passing the board's known `403` down into the stream. That fixes the board and
  leaves everything else: `use-shell-context.ts` subscribes to the same
  connection independently since LAI-122, so on any screen where `BoardScreen`
  is not mounted there is nobody to supply the `403`. The Notes predate the
  shared connection. `readyState` inside `onerror` needs no extra request, no
  pre-flight `fetch`, and no state threaded between components.

- *Accepted that the fix is status-blind.* It knows the browser gave up, not
  why. A `500` reads `CLOSED` too — and that is an improvement, not a
  compromise: today a `500` on the stream silently kills live updates under a
  pill still claiming to reconnect. The board already renders the precise reason
  from its own `403`; the stream's job is only to stop contradicting it.

- *Moved the decision out of JSX.* Three places described the stream and all
  three were wrong together — banner, pill, rail. A decision spelled out inline
  in three components is one no test can reach, so it went into
  `stream-presentation.ts` with an exhaustive `switch`, which makes a new
  `StreamStatus` a type error at each place that must describe it.

- *Forget a refused stream, and guard the forgetting on identity.* Left
  registered, a dead source gets handed to the next subscriber, which waits for
  frames that cannot arrive and never sees the refusal — it already fired.
  Dropping it means one fresh attempt on the next mount, which succeeds if
  access has since been granted. But dropping it also made the existing
  unsubscribe unsafe: it deleted by key, so it could evict a replacement another
  subscriber had opened. Now guarded on identity.

**Discovered**

- *The task's second criterion described a defect that does not exist, and I
  measured that before being told.* LAI-224 says the stream "retries for ever,
  roughly every three seconds". A real browser against this server fires
  **one** error on a `403`, sets `readyState` to `CLOSED`, and never retries;
  the server log shows one request. CORE (who filed it) and CHIEF both sent me
  the same correction while I was building. My numbers, independently:

  | case | `error` events | `readyState` | requests |
  | --- | --- | --- | --- |
  | `403` | 1, at 10ms | `2` CLOSED | 1 in 12s |
  | SIGTERM mid-stream | one per attempt, ~3s apart | `0` CONNECTING | continuous |

  What actually persisted was the **banner**, not the requests — one `onerror`
  mapped to `dropped`, and nothing ever arrived to move it off. `attempt 1` was
  the tell: a real three-second loop reads `attempt 80` by the time you look at
  it.

- *A latent bug in my own test harness, invisible because nothing used it.*
  `FakeEventSource` built itself with `Object.assign(this, { get onerror() {…} })`.
  **`Object.assign` copies a getter's value, not the accessor** — so `onopen`
  and `onerror` became plain `null` data properties, the module's assignments
  went into the instance rather than the record behind it, and firing them from
  a test did nothing at all. Every existing test drove `addEventListener`
  handlers, so it had never been exercised. Rewritten with real class accessors.
  My first run failed with "no connection at 0" three layers away from the
  cause, because the broken fake also leaked live streams into later tests.

- *The drop path is not monotonic.* The stream **reconnected successfully**
  7.4s after SIGTERM, during the server's drain window, then failed again at
  14.4s. A fix that assumed "once dropped, always dropped" would have been
  wrong, and neither correction I was sent mentions it.

- *I misread the browser console and nearly filed a task for it.* Eight
  identical `/projects/laika-core` entries in 26ms looked like a fetch storm.
  The server log records **one** request — the console was repeating one failed
  resource. Checked before filing; nothing filed. The server log is the
  authority, not the console.

## 13:20 +05:30 — correction to the LAI-224 entry above

**I submitted LAI-224 without finishing the task file, and did not notice.**
CHIEF caught it at review: no criteria ticked, `status: in-progress`,
`finished:` empty. `b39ac70` recorded the task file as
`1 file changed, 0 insertions(+), 0 deletions(-)` — a pure rename.

**What happened.** I edited the file, then ran `git mv`. **`git mv` stages the
rename from the index, not the working tree**, so the commit carried the
*pre-edit* blob and my ticks stayed behind as an unstaged modification. I then
"verified" by grepping the file on disk, which of course showed exactly what I
had just written.

**This is the second time.** LAI-070 was the same mistake, and the rule I wrote
for myself afterwards — *read the field back from `git show`* — is precisely the
check that would have caught it. I had the guard and used the weaker version of
it. Grepping the working tree cannot distinguish "edited and committed" from
"edited and not staged"; only reading the commit can.

The correct check, after any edit-then-move:

```bash
git show HEAD:.tasks/review/LAI-00X-*.md | grep -n '^status:\|^finished:\|^- \['
```

Discarded my stale working-tree copy on merge — `.tasks/` resolves in CHIEF's
favour and they had already ticked against their own verification, which is the
better record anyway. Nothing of substance was lost: the measurements and
reasoning from that build note are in the entry above, which did commit.

**Cost.** A reviewer had to reconstruct what I was claiming before they could
start on the substance. CHIEF verified it independently and accepted it — three
mutations, three reds, and both paths driven in a browser against a fresh
database — so the fix stands. The waste was entirely mine to prevent.

**Also noted, and accepted:** appending a note to `.tasks/backlog/LAI-217` was
not mine to do. `.tasks/` is CHIEF's and the `[ops]` exception is CHIEF-only —
§2 says so plainly and I read it as covering a transparent, useful addition. It

### Precision on the note above — the gate does typecheck components
