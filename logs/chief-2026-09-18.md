**Decisions**
- **Two tasks, not one, and the SPEC row lands with the column.** This is
  CLAUDE.md §4.4 — `schema-spec-drift.test.ts` reads every §4 table against
  `schema.ts`, so adding the §4.5 `position` row now would redden `master`
  before any column exists. The two SPEC lines are quoted verbatim in LAI-472
  and I apply them at merge time (§4.4 step 5), rather than writing them today.
- **No new `ACTIVITY_TYPES` verb.** A reorder writes `task.updated` with
  `{ field: 'position' }` — the shape §4.8 already uses for tags. The
  alternative, a `task.reordered` verb, is **always three owners** (the client
  mirrors the list, the dashboard needs wording), and §4.8's own test fails for
  it: *"when did this card become third in the lane"* is not a question the feed
  is for. The row is still written, because §11.5 names SSE frames after the
  §4.8 type and a second viewer needs one; the **feed suppresses** it instead.
  Storing and displaying are separate questions, answered differently on purpose.
- **One sequence per project, not one per lane.** A per-lane position is only
  meaningful beside a `status`, so every status change would have to invent a
  new one. The cost is that a cross-lane drop must write both status and
  position — named in D-060.3 and made a criterion rather than left to be
  discovered, because without it a card dropped at the top of `TODO` surfaces in
  the middle of it.
- **The representation is left to CORE**, with behaviour pinned instead: one row
  moves, 60 repeated drops into the same gap still work, two concurrent drags do
  not collide. Naming "fractional midpoints" in the task would have been me
  deciding CORE's implementation from a guess about `REAL` precision; naming the
  **trap** lets them choose and proves it either way.
- **The keyboard path ships with the drag, not after it.** A board whose
  ordering is mouse-exclusive has made the order itself unreachable, and
  retrofitting means rebuilding the interaction.
