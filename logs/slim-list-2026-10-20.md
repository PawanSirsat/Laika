**Decisions**
- Only `slim` is accepted. Any other value is `400` naming `fields`, so a
  typo cannot quietly get the heavy shape. An empty value reads as absent,
  as every filter's does.
- `listTasks` on the web always sends `fields=slim`, with no option. All
  three callers are lists, so "every web list fetch is slim" holds by
  construction, and a unit test pins it.
- I split the type rather than making the two fields optional. With
  `TaskSummary` as its own type, the compiler finds every reader of the texts
  off a list. It found four, all in the panel. Optional fields would have
  compiled silently.
- The store passes a write's full answer through `toSummary`. Otherwise the
  next slim read differs by two fields and the card glows for a change nobody
  made.
- The panel reads the texts again only when the store's `updated_at` moves
  past its copy. A `PATCH` is the only way the texts change, and it always
  moves `updated_at`. The panel's own edit is accepted from the `PATCH`
  answer, not read back.
- While the read is in flight, the description holds its place and is not
  editable. An empty, editable description could be saved over the real one.
- Search stays on title, key and outside id, and SPEC §11.4.1 says so. It
  never matched descriptions, so nothing was lost. A server-side `q=` would
  be a new feature.
- I did not file the review-queue follow-up. The orchestrator files in this
  block on `master`.
