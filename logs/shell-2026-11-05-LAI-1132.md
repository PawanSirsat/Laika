**Decisions**
- The pane is a `::before`, never the element. `backdrop-filter` makes an element the
  containing block of its `position: fixed` descendants; the sidebar holds a fixed popover
  and catcher, the space bar a fixed menu, modals the Dropdowns portalled into them
  (LAI-726). Blurring the host would have trapped and clipped every one.
- Modal surfaces are translucent level 3 over a *blurred scrim*, not blurred themselves:
  one blur per modal, and a Dropdown inside stays real glass rather than a nested blur.
- Lanes and in-content cards are a tint, not a blur: only the smooth ambient gradient is
  behind them, so blur would cost GPU and change nothing visible. Keeps the board at 3
  blurred layers (sidebar, header where shown, space bar).
- Anything floating inside chrome (spaces popover, user menu) stays solid-on-glass — the
  "never nest" rule applied literally.
- Fallbacks swap tokens rather than restyle components, so every consumer follows.
- No ambient drift animation: every blurred layer above it would re-rasterise each frame.
- Matched the owner's references in docs/design/ (main checkout): ambient and dark glass to
  laika-brand-board.png (Ink→navy diagonal, Mist haze, corner discs with a line of light,
  fine-bordered translucent navy panels); light to laika-logo-light.png and
  laika-loaders.png (lavender-cast Paper, Glacier discs, white glass). No lavender in the
  dark background — the board keeps it for the mark.

**Discovered**
- The build's minifier folds `-webkit-backdrop-filter` and `backdrop-filter` into one
  declaration and keeps the last; with the prefixed line second, every blur was silently
  off in Chromium. Unprefixed only now, and the guard refuses a `-webkit-` twin.
- A `body` background paints above `body::before` at `z-index: -1` (it is an in-flow block
  background), which hid the ambient layer entirely. `html` keeps the canvas.
- No SidePanel on this branch holds a real Dropdown; the B16 test and the screenshot place
  a `.dd-panel` in a real SidePanel with the real stylesheet.
- Board-wide z-indexes outside the shared surfaces (board 30/31, timeline, my-day) are
  left as they were — moving them is O21's sweep, not this task.

  so the peak moves `#a2afd0 → #8798d6`. Glass goes from 0.58/0.68/0.80 to 0.56/0.62/0.74. The

**Decisions**

  light is 4.63:1 (5.16 before). The margin was spent on visible ambient, as asked.
- The sheen is brighter. The AA pairs measure the level's tint only, which was already true
  before this change. The theme.css comment now says so, rather than claiming more than the test
  proves.

## 2026-11-06T01:40:00Z — LAI-1132 (CI failure on PR #291's base, 2e9b9fed)

CI run 42089167912, job "Gate · web 1/4", failed at `task-panel-editing.test.ts:439`, "the
same affordance in dark". The assertion that failed was "priority shows nothing on hover",
and the hovered background read `rgba(0, 0, 0, 0)`.

**Root cause.** No token was involved. `--bg-column` (the hover colour) is unchanged and
resolves to `#121826` in dark. The cause is that `[data-editable] { transition:
var(--transition) }` faded `background-color` in from transparent. A transition only moves
when a frame is rendered. Before the first frame, a hovered part already matches `:hover` but
reads its start value, which is transparent.
- Measured locally: at 0 ms after the hover, the part matches `:hover` and reads
  `rgba(0, 0, 0, 0)`. At 50 ms it reads `rgba(18, 24, 38, 0.694)`.
- With the animation timeline frozen (CDP `Animation.setPlaybackRate 0`), every editable part
  reads `rgba(0, 0, 0, 0) -> rgba(0, 0, 0, 0)` in both themes. That is CI's failing pair.
- Locally the test passes at both 2e9b9fed and c388c9b1, including three runs of the dark test
  on the base tokens. So in CI the read 150 ms after the hover came before a frame.
- That glass is what slowed the frames is an inference, not a measurement. Glass added blurred
  layers, which a GPU-less runner rasterises in software, and the brand PR passes the same
  test. The CI log was not available yet because the run was still in progress.

**Fix.** server/web/src/routes/screens/task/task-panel.css: the `[data-editable]` rule and its
`var(--transition)` are gone, with a comment saying why. The soft hover background now applies
on the hover's own style change, with no frame to wait for. The test is unchanged. Task cards,
forms and the hover colour token are untouched. The other `var(--transition)` uses in the file
(`.meta-chevron`, `.sub-progress-fill`) are not editable parts.
- With the timeline frozen after the fix, every part reads `rgba(0, 0, 0, 0) -> rgb(18, 24,
  38)` in dark and `-> rgb(232, 237, 244)` in light, on the c388c9b1 tokens.
