**I read the shape off the design rather than inventing it.** The prototype's
card rows carry tags positionally — `['LAI-157', 'todo', …, ['ui'], …]` — and one
task holds `['agent', 'core']`. That single row settles the data model: **many-to
-many**, so a join table, not a column. Nine tags appear across the file
(`agent ai audit auth billing core infra presence ui`), all short lowercase
single words, every chip rendered in the neutral `--tub`/`--bd` pair.

Decisions and why, all in D-027: project-scoped (a `ui` on the server project is
not the `ui` on the web one); lowercase enforced at the database (case-variant
duplicates are precisely what makes a tag filter worthless); created by being
applied, no separate step; **no colour column**, because the design never asks
for one and it would mean a palette decision and a settings screen; flat, no
hierarchy. Policy **reuses existing §3.2 cells** — applying is `task.write`,
renaming project-wide is `project.settings.edit` — so no new action. Activity is
`task.updated` with `{field:'tags'}`, deliberately **not** a seventh §4.8 verb.

**I broke master writing it, and the check I commissioned caught me.**

Adding §4.16 to `docs/SPEC.md` immediately failed LAI-051's
`has a table for every §4 section` — the spec declared `tags` and `task_tags`
and `schema.ts` had neither. Exactly right, and exactly the class of error that
broke master twice before I had these checks.

**Reverted the SPEC edit and parked the §4.16 text verbatim inside LAI-079**,
which PM adds on acceptance (`docs/` is not a builder's to edit). **A red master
is worse than a temporarily undocumented feature** — it blocks both builders'
gates. Kept D-027: a decision is not a schema, and nothing checks DECISIONS.md.
Master verified green after the revert: 731 + 206.

**But the revert exposed a real gap, and I filed it rather than living with it.**
D-011 makes the spec authoritative, which means **the spec leads the code by
design** — so the interval between deciding and building is normal, and the drift
check treats it as failure. My only options were red master or no spec. **LAI-080**
asks for a per-section "specified, not yet built" mark that **names the task that
closes it and fails once the table exists**, so the exemption cannot outlive its
reason. Explicitly told them not to weaken the check: a blanket ignore returns us
to having none.

Third time this lesson has come round (LAI-054, LAI-048): a guard is only worth
having if it can fail, and only worth **keeping** if it cannot fail for a reason
nobody can act on — a check that goes red on a legitimate state trains people to
route around it. Here that meant not writing the spec at all.
