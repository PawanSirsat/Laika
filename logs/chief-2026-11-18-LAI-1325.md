**The question CHIEF asked first: which credentials does the board take?**

No policy change was needed, so I did not stop for a plan.
- The collector's routes ask org actions:
  - `GET /me/activity-sharing`: `activity_sharing.read_own`;
  - `PUT /me/local-activity` and `POST /otlp/v1/metrics`: `local_activity.send_own`;
  - `GET /me/time-settings`: `time_settings.read_own`;
  - `PUT /me/time-drafts`: `time_drafts.send_own`.
- A registered agent's token keeps exactly those org actions (`AGENT_TOKEN_ORG_ACTIONS`, SPEC
  §6.2) and is refused every other one. Consent (`PUT /me/activity-sharing`) and reading back
  or erasing (`GET`/`DELETE /me/local-activity`) are session only. So D-102's "a token cannot
  turn it on" holds whichever token sends.
- **CHIEF's "`GET /me/local-activity` (the sharing answer)" is `GET /me/activity-sharing`.**
  `GET /me/local-activity` is the session-only read-back.
- **The device credential is an ed25519 key**, not a bearer token, and the board takes it only
  on pairing. The usable credential on a device-paired machine is a tool's own: the registered
  agent's token `laika tool add` saves in `~/.laika/agents/<tool>.json`.
