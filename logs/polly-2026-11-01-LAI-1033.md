**Decisions**
- **Matched by `created_at`, only past the newest journal `when`.** That is
  the migrator's own key. A rollback's journal is a prefix of the newer one,
  so every unknown row is past its end. Refusing middle rows would gamble a
  deploy outage on a case nobody has seen.
- **The restore triggers on "this run wrote a snapshot", not on the refusal.**
  Both lose the same data, and that data is kept aside either way. This trigger
  also covers an old image without the guard, which is the first rollback after
  this ships, and saves the 90-second refusal.
- **The marker carries the run id.** Without it, a deploy that failed before
  reaching the instance would leave the last good deploy's marker. The
  rollback would then restore the snapshot taken after that deploy, losing
  everything since. A test and a mutation pin this.
- **The oldest snapshot since the marker, not the newest.** A crash-looped boot
  re-snapshots a half-migrated file.

## 2026-11-01T16:31:54Z — LAI-1033 review round 1 (B1 and three notes)

**What changed**
- `.github/deploy/host-restart.sh`:
  - **The restore never leaves `laika.db` missing.** The snapshot is copied
    to `laika.db.restoring`, the original is hard-linked to
    `laika.db.rolled-back-<ts>`, `-wal`/`-shm` move aside, then a rename
    puts the copy over `laika.db`.
  - **Every step checks its result**, because a function called from `if`
    runs without `set -e`. On failure `undo_restore` puts the files back,
    the log says `restore: FAILED`, the previous image starts on the original
    database, and the script exits 1 even when that comes up healthy.
  - **Both modes refuse** when `laika.db` is missing beside
    `laika.db.rolled-back-*`.
  - **`this_deploys_snapshot` no longer fails** on a missing backups directory.
  - **The marker is written before `docker rm`**, and `sha256sum` cannot
    fail the step.
- `.github/workflows/deploy.yml`: the restart step gets `id: restart`. The
  rollback runs only when `tag` or `restart` failed, so a failed ECR
  clean-up after a verified healthy deploy no longer rolls back.
- `.github/deploy/deploy.sh`: the run id comes from `LAIKA_DEPLOY_RUN`, else
  `GITHUB_RUN_ID-ATTEMPT`, else `local-<UTC>-<pid>`; the script prints it.
- `server/src/db/migrate.ts`: the marker comment now says only that the script
  prints "restore is manual" when it sees the marker.
- `server/test/tooling/host-restart.test.ts`: 13 tests (was 5). New: `-shm`,
  a failed copy, a failed final rename after the `-wal`/`-shm` moves, a
  missing backups dir, deploy and rollback refusing with only kept copies, and
  three run-id cases.
- docs/AGENTS-ROLLOUT.md § 7: restore steps, failure path, refusal, trigger,
  manual run id.

**Decisions**
- **Undo after a hard link:** a rename onto the same inode is a no-op that
  leaves both names, which the first test run found. When `aside -ef DB`,
  the extra name is removed, and no data goes with it.
- **The rollback does not run after a verified deploy whose clean-up failed.**
  An image-only rollback there is exactly the state this task removes.
- **Refuse in rollback mode too, not only deploy.** The same empty-database
  risk applies.

**Mutations** (host-restart.test.ts, each anchor-checked, restored from HEAD):
- Killed: no-undo, not-red, no-refuse, no-shm, run-id-fixed.
- Backups guard: removing the `-d` check alone survives (`|| true` on
  `find` covers it); removing both is killed. Redundant by design.
- Not observable by these tests: whether `laika.db` was missing *between*
  steps. Only the end state is asserted, and the undo restores it either way.
- Not tested here: the workflow's `if:` expression.
