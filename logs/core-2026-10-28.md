## LAI-562: a project-pinned token cannot mint a wider token

- **When:** 2026-10-27T20:36Z to 20:55Z (UTC)
- **Where:** Belka, dispatched by CHIEF/polly. Worktree `Laika-pin-mint`,
  branch `LAI-562-pinned-token-cannot-mint-unpinned`, base `28b879a9`
  (#98 + PR #96, H4).

**Changed**
- `server/src/services/tokens.ts`: `createToken` calls a new
  `assertWithinOwnPin`. A token-borne mint must name a subset of the caller's
  pin. `null`, or any id outside the pin, is `403 forbidden` with
  `details: { action: 'token.create_own', reason: 'project_pinned', project_ids }`.
- `server/test/services/tokens.test.ts`: 4 tests in a new describe, covering
  `null`, a wider list, a subset, and unchanged unpinned/session behaviour.
- `server/test/http/middleware/auth.test.ts`: 2 tests.
  - The pinned token is refused three wider asks, then mints a subset that
    reads `inside` and not `outside`.
  - A `read_only` token is refused any mint.
- `.tasks/backlog/LAI-563-token-mints-later-expiry.md` filed (board LAIKA-815).

**Decisions**
- Refuse rather than narrow, matching H4 and `assertReadableProjects`'s
  "never silently narrowed".
- The check runs before the existence check, so a pinned token learns nothing
  about which ids exist.
- No scope check was added to the service: `can()` already refuses a
  `read_only` token `token.create_own` (it is not a read). The code would be
  unreachable, so a test pins the behaviour instead.

**Discovered**
- Before this, a wider *list* was already refused, as `422` via
  `canSeeProject` reading the pin. Only `null` escaped.
- No MCP tool mints a token, so REST is the one path.
- Expiry can still widen: filed as **LAI-563**.
- Tokens minted unpinned by pinned tokens before this fix are not revoked.
  The PR gives an operator query.

**Mutation check**
