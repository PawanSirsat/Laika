## 2026-10-28T10:30:00+02:00 — LAI-539 (review FAIL → fixed)

**What changed**
- server/src/http/routes/events.ts — the write-time check is now `writable(item)`, run on **every** frame of a token stream (`ready`, `gap`, each live or replayed row, each keepalive) as it reaches the front of the write queue: a fresh `reloadActor`, and each row filtered again with `insidePin` + `visibleTo` against that fresh actor. The per-batch `recheck` flag and the stale `latest` actor are gone.
- server/test/http/routes/events.test.ts — new `every frame on a token stream is checked as it is written (LAI-539)` block (9 tests); `bareApp` gains `afterAuth`.

**Decisions**
- Per-frame `reloadActor` on token streams, not an in-process credential-version counter: a counter must be bumped at every write site that can change the answer (and expiry is a clock), so a missed site would leak silently. Cookie streams keep their batch-level checks.
- Writes are held deterministically in the tests through the `TransformStream` backpressure (`streamSSE`'s readable side has a high-water mark of 0): one unread frame holds the next write, so the frames behind it are provably still queued when credentials change.

**Correction to the 01:40 entry above**
- It said the window between the batch check and later frames was "microseconds" and covered by the per-frame `insidePin`. **Both claims were wrong** (Codex cross-vendor review of PR #100). A slow client holds every write via backpressure, so the window is as long as the client takes to read, and `insidePin` read the `latest` actor captured at the batch's first frame — stale for every later row. `gap` and keepalive frames had no write-time check at all. The fix above closes all three.

**Discovered**
- Minting a token writes an org-level `token.created` row that an unpinned owner's token stream does see; the replay tests mint before taking the starting seq for that reason.

## 2026-10-28T16:30:00+02:00 — LAI-539 (review round 2 FAIL → fixed)

**What changed**
- server/src/http/routes/events.ts — the refusal `error` frame has its own terminal slot (`terminal`), outside the queue. It is chained after the queue's current tail, so it follows any write in flight, and it bypasses both `ended` and `MAX_QUEUED_FRAMES`. It is set once and awaited (`terminalWritten()`) after the queue drains, before the response closes. `enqueue` takes nothing once `refused`, and queued frames skip, so the error is the last frame. The `refusal` flag on queue items is gone.
- server/test/http/routes/events.test.ts — 3 tests: a refusal found while a shutdown drains; a refusal with the queue at its cap; a gap refused by its own check after `ready` is written.

**Decisions**
- A separate slot rather than an exempt queue item: both of the queue's refusals (`ended`, the cap) are right for every other frame, and the slot is the only frame they must not apply to.
- The gap test uses the injected clock as a trigger, revoking on the third credential check (auth, `ready`, `gap`), and asserts the clock was read exactly three times. A backpressure hold cannot do this, because `ready` is the first frame in the stream and nothing sits ahead of it to hold it.

**Discovered**
- `ready`'s write resolves a few microtasks after its step runs, so a test that fills the queue synchronously right after connecting counts `ready` as queued and trips the cap one frame early. My first cap test did exactly that: it exercised the already-`ended` path a second time, and the cap mutation survived. A probe (since removed) showed it. The test now settles first and asserts the stream is still open before the refusal.
- PR #102's `reloadActor` must call `tokenContextFor()` when the two land together. This is noted in the PR body.

In review (PR #100 updated).
