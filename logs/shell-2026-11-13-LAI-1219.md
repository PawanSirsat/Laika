**Decisions**
- **CSS is not split, and the entry stylesheet is the old one rule for rule.**
  Splitting JS let each chunk bring its own CSS, and the board's lanes stopped
  scrolling (`board-refresh.test.ts` red): `.board-main` lives in
  `board/board-rail.css`, which only `activity/ActivityPanels.tsx` imports — it
  had worked only because every stylesheet was global. Per-chunk CSS would also
  make the cascade depend on visit order. `cssCodeSplit: false` was tried and
  rejected: it keeps CSS global but reorders it (the shell's CSS moved ahead of
  the screens', 5,808 of 7,531 rules out of sequence). Instead `ScreenOutlet`
  imports `screen-styles.ts` first, where it used to import the screens, and
  the three sheets the base build had hoisted into their own links come first
  in AppShell. Verified against a build of 844319cc: identical 7,595-rule
  sequence (the only byte difference is the two joins between what were three
  files). The guard that keeps the list complete is the build test's "no
  screen chunk brings CSS of its own".
- **One initial chunk** (`$initial` group). Without it Rolldown moved code the
  shell shares with a screen into ~15 siblings, all modulepreloaded up front —
  the `index-*.js` number alone then looks smaller than what the page loads,
  and those siblings took their CSS out of order (`button.css` after the main
  sheet). The budget test therefore measures the entry **plus** its static
  imports, so a regrouping cannot fool it.
- **Try again asks for a fresh URL.** Measured in the harness's Chromium: a
  failed dynamic `import()` is remembered — the same URL rejects at once with
  no request, even after the network is back. So a failed module is retried at
  `<url>?retry=N` (the URL is read from the rejection's message; Chromium and
  Firefox name it, Safari does not). The first attempt never evaluated, so
  nothing runs twice. If the retry fails too — a shared dependency the browser
  remembers failing, or a deploy that renamed everything — the next Try again
  reloads the page, and the error body says it will.
- **A failed screen gets a fresh `lazy` only after Try again** (a retry
  generation in `screen-chunks.ts`). The first version remade it whenever it
  rendered after a failure; React re-renders a rejected lazy by itself, so it
  fetched, failed (cached) and suspended forever — the screen sat on its
  loading state. Found by the failure test, pinned by mutation M3.
- **An arrived chunk renders directly**, chosen once per mount. A preloaded
  screen therefore never suspends (no placeholder at all); a sibling in a
  grouped chunk does not suspend for a tick either.
- **The boundary softens chunk failures only.** Any other error a screen throws
  is rethrown, exactly as before the split (there was, and is, no app-level
  boundary — not this task's to add).
- **Preload targets.** Sidebar entries, space rows, the create-space links and
  the space view tabs. Not `PageTabs` (Inbox/Insights/Organisation/Developer
  tabs): their screens are already in the same chunk. The board — the default
  — is warmed one frame plus one task after first paint, signed in only.
- **Budget 150 KiB** against 134,915 B: ~14% headroom; a large screen pulled
  back into the entry fails it (mutation M1: 221,700 B). Under the `docs/ux`
  200 KB ceiling on purpose.
