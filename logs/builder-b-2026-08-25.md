### The bug worth writing down

I wrote a `gap` handler whose comment said *"a gap we cannot parse is still a
gap; the consumer reloads wholesale"* — and it did not. It set `catchUpFrom`
only when the frame carried a numeric `updated_since`, and `BoardScreen` only
reloaded when `catchUpFrom` **changed**. So:

- `unknown_last_event_id`, which carries `updated_since: null`: no reload.
- an unparseable body: no reload, despite the comment saying otherwise.
- two gaps with the same watermark: one reload.

The board would have sat stale under a pill still reading `LIVE` — the exact
failure the `gap` frame exists to prevent. **The comment described the intent and
the code did something else, and both typecheck and the tests were green.**

Fixed by making `seq` rise on every gap regardless, extracted as a pure
`nextGap()` so it could be tested against the server's real frame bodies. Proven
able to fail: restoring the old behaviour turned 3 tests red.

I only found it because I went looking for what the server actually sends rather
than trusting what I had written down. Reading `resumeFrom()` is what showed
there are **two** gap shapes and only one has a watermark.

### Verifying against a running instance, not by reasoning

Everything was driven on `:3370` — the owner's `:3000` container untouched, and
I confirmed which SQLite file my process had open before writing to it rather
than assuming.

The one that needed a real experiment was `gap`. First attempt produced nothing,
and the reason was **correct behaviour**: the page had received no activity frame
since load, so `EventSource.lastEventId` was empty, no `Last-Event-ID` was sent,
and the server rightly resumed from head. So: create a task to establish a
resume point, stop the server, insert 600 rows (`MAX_REPLAY` is 500), restart.
That produced the catch-up — and a **control run** (restart, nothing missed)
produced zero requests, which is what makes the result mean anything.

### How I found it

Not by reading the design — by listing which screens import `ScreenHeader` and
which do not. Three did, three did not, and the split was invisible in any
individual file. Worth repeating as a technique: the interesting question was
not "is this screen right" but "which screens disagree with each other".

### The wrapper padding, which is the part that would have been missed

All three screens had `padding: var(--space-4) var(--space-5) var(--space-6)` on
their wrapper. Dropping `ScreenHeader` in without touching that gives a header
bar **inset from both edges** — which still looks deliberate, still passes every
test, and is not the design's header bar. The Board avoids it with no padding on
the wrapper and `> :not(.screen-bar)` insetting everything else; all three now
do the same. Measured `left: 213px` against a 212px sidebar to confirm it rather
than trusting the screenshot.

### Scope I went past, deliberately

The goal named three screens. I converted **five**. AC4 asked for a guard that
fails when an in-app screen renders its own heading, exempting only pre-auth
screens — and `Screen.tsx` and `NotFound.tsx` both render inside the shell with
their own `screen-head`. So the AC forced a choice: convert them, or write two
exemptions with no reason behind them. Exemptions nobody can justify are how the
original inconsistency survived in the first place, so I converted them. One
line each. `screen.css` was then empty and went.

Stated in the task file too — PM should see it, not discover it.

### Honesty in the context lines

Each context is derived. Two of them stay **silent** instead of guessing:
Sprints omits it until the list is `ready`, Dashboard omits it entirely while
loading. And where a list hit its page cap, the count renders `4+` rather than
`4` — the number is a floor, and printing the floor as a total is the screen
asserting something it does not know. That `truncated` flag already existed and
nothing was reading it.

### Dead CSS, again

Third time this pattern has come up in this repo, so it is worth the line:
removing a heading and leaving its CSS is what breaks the replacement later. I
removed `.timeline-head`, `.timeline-title`, `.sprints-head`, `.sprints-title`,
`.dash-head`, `.dash-title` with the markup, and deleted `screen.css` outright
rather than leaving a file of rules matching nothing.
