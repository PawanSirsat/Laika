**Decisions**

- **`can()` per proposal is not a table in this file.** Each proposal calls the
  service a person would have called, and each of those runs its own
  `assertCan`. §3.2's rows therefore decide each change, and there is no second
  opinion here to fall out of step with them. The case that makes this concrete:
  `meeting_proposal.apply` is member-and-up, but a `decision` writes
  `context_md`, which is lead-only — **so a member may apply one proposal in a
  review and not another.** The test proves both halves *and* that the owner can
  do the one the member could not, so the refusal is provably about the role
  rather than about the proposal being unapplicable.

  Same reasoning `finishTask` gives for not re-checking its halves, and the same
  §3.4 gives for the webhook performing `task.write` rather than an action of its
  own: the principal is what differs, not the operation.

- **A `decision` is not a no-op; §11.4.2 says so.** The task file's Notes
  wondered whether accepting one might change nothing. §11.4.2: *"Accepted
  `decision` proposals from a meeting diff append to it with the date. That is
  the mechanism that keeps it current instead of stale."* So it appends. One
  `## Decisions` heading created once, one list across meetings, an ISO day
  rather than a locale because the document is read by whoever opens it.

- **One `meeting.applied` row for the set, not one per proposal.** AC5 reads
  *"**Every applied proposal** writes `meeting.applied` … with **which
  proposals** in the payload"*, and those two clauses point opposite ways. §4.8
  decides it rather than my preference: **`sprint.tasks_changed` is one verb for
  both directions "and the payload carries which"** — the identical shape, a set
  operation with one row. The property §4.8 actually demands is its own stated
  test, *"could a reader answer 'when did this happen?' without inspecting a
  payload?"*, and one row passes it.

- **Idempotence is per proposal, stamped into `proposals_json`.** The review's
  `status` column cannot carry it: it is one column for a set, so a client that
  posted, lost the connection and retried would either double every change or be
  refused wholesale. A retry after a dropped response is the ordinary case this
  criterion exists for.

- **Expiry is read from `expires_at`, not only from `status`.** §11.6's sweep
  runs on a schedule, so between lapse and sweep the row still says `pending`.
  The timestamp is the truth, and there is a test for exactly that window.

- **`change` proposals are validated at apply time.** `changes` arrives as
  `Record<string, unknown>` straight off the model — `parseProposals` stores it
  without inspecting it, because §10.2 does not say what may be in it — so an
  unrecognised key is **refused, not dropped**. Dropping it is the whole bug in
  miniature: a human accepted a proposal that read *"set priority and reassign"*,
  and an apply performing one of those has applied something nobody accepted.
