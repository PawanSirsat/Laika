**Decisions**
- Reachability, not fetch-by-SHA: measured that a local `git fetch <path> <sha>` succeeds for a dangling commit, so "fetched" proves nothing about publication. The target must be an ancestor of a branch or tag tip from `ls-remote`; tips are fetched by id with `--no-write-fetch-head`, so no ref or FETCH_HEAD is written in the user's checkout.
- Only a full 40-character id is a pin; a short `build_commit` is refused.
- Plain-http board off loopback: refused for the update unless `--allow-http`; `--check`/`--dry-run` warn. Found by running it for real: the owner's own board is `http://<ip>`, so an https-only rule would make the command unusable there. This is a deviation the reviewer should decide on.
- `http:`/`git:` sources refused, credential-bearing sources refused without printing them; an argument starting `-` is refused (git option injection).
- MCP config is not rewritten: entries carry the board URL and a variable name, never a checkout path, so there is nothing to re-apply. The files are hashed before and after instead, and a change fails the update. Only agent-session hooks are re-applied, and only where already on; activity hooks are not touched.
- Runtime dependencies: `cli/` has none, so "install deps in staging" is a check — a target whose `cli/package.json` gains `dependencies` is refused rather than half-installed.
- Hook-file backups are deleted after a verified update (settings.json can hold a personal token); `state.json` with the previous commit stays.
- `--dry-run` fetches nothing, so it cannot say whether the target is published or the checkout diverged; it says which steps it would run.
- Recovery rolls back even an update that was verified but killed before its marker was removed; re-running is cheap, guessing is not.
