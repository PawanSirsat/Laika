## 2026-09-01T09:35:00Z — LAI-409

**What changed**
- `server/test/mcp/parity.test.ts` (new, 15 tests)

**Decisions**
- **`finish_task`'s twin is a composite, not an exemption.** There is no
  `POST /tasks/:id/finish`. A human finishing work does two things — moves the
  task to review, and says what they did — so the twin is those two REST calls
  in sequence. That is a real pair rather than a second exemption, and it is
  precisely what proves LAI-408's one-transaction service did not become a
  third write path. Had I exempted it, the one tool most likely to drift would
  have been the one nothing checked.
- **Two clean databases per pair**, so the comparison is structural rather than
  an artefact of one run following the other.
- **`normalise` strips ids, clocks, `actor_kind` and `actor_token_id`** — and a
  separate test asserts the last two *do* differ. Without it the parity tests
  would pass on a tool that forgot it was an agent, which is the one thing an
  agent's row is supposed to say.
- **Compared through `GET /projects/:slug/activity`**, which serialises with the
  same `eventView` the SSE stream uses — so this compares what a browser
  receives, not what the table stores (AC5).
- **Both directions of the derived list.** A tool with no pair is named; so is a
  pair for a tool that no longer exists. A stale pair reads as coverage and is
  not.

**The mutation that taught me what this test actually guards**

My first attempt at AC6 mutated the **shared service** — `createTask` writing
`task.updated` instead of `task.created`. The `create_task` pair **stayed
green**, and something else went red.

That is the property working, and it took a minute to see: both sides call the
same service, so changing it moves them together. **Parity cannot be broken by
changing the thing both halves share** — which is exactly what the layering
rules guarantee, and exactly why CHIEF was right that this test *confirms* a
structural property rather than propping it up.

The mutation that matters is the **tool diverging from the route**. All three
name the tool:

```
× create_task — identical activity, differing only in attribution
× start_working — identical activity, differing only in attribution
× list_projects — identical activity, differing only in attribution
```

- `create_task` writing an extra comment the route does not → red.
- `start_working` reaching for `changeStatus` instead of `claimTask` → red.
  That one is the realistic failure: a plausible-looking substitution that
  produces a different verb.
- A read tool writing anything → red.
- A REST twin for `log_unlisted_work` appearing → the self-expiry fires and
  says to remove the entry.

**Discovered**
- **A mutation that goes red is not automatically a mutation that proved
  anything.** My first one went red on *"the agent's rows say agent"* — a
  different test entirely — and I would have recorded AC6 as satisfied had I
  only read the exit code. The harness prints the failing test name for exactly
  this reason, and this is the second time today that reading it mattered.
- **My second mutation did not write anything.** I "made a read tool write" by
  adding a `listTasks` call — which is a read. It stayed green because the code
  was still correct, not because the test was weak. Both of my first two
  mutations were wrong in different ways, and the test was fine.
- **`pnpm typecheck` caught two errors `pnpm test` did not** — an unused
  parameter and a `Map` literal whose element type TypeScript inferred from its
  first entry, so the one carrying a `note` no longer matched. Sixth occurrence
  today; LAI-136 is filed and now p2.
- nothing filed.

  `server/test/services/heartbeats.test.ts` (new, 9)
- `server/test/policy/*`, `tooling/policy-spec-drift.test.ts` — the new action

**Decisions**
- **Asked before building, for the third time.** §3.1 had no cell and AC3 says
  stop and file rather than reuse something plausible. CHIEF ratified the row
  unchanged. It costs one message and nothing has had to be unpicked.
- **Token-only is enforced in the route, not by `can()`.** §9.1 restricts the
  *credential*; §3.1 grades by *role*. `can()` cannot express it, and a cookie
  resolves a perfectly good actor — which is exactly why the refusal has to be
  explicit rather than assumed to fall out of the permission check.
- **No `activity` row.** §4.8's verb is `heartbeat.session` — a session, not a
  ping. CHIEF checked §4.8 independently before agreeing. Said in a comment so
  the absence reads as a decision.
- **`matched_task_id` stays null and `202` rather than `201`.** §9.2 is M5, and
  nothing is created that a client can go and read.
- **Bounds in the service as well as the route**, because the plugin and a
  future MCP tool reach it without passing through zod (LAI-404's lesson).

**Two things the tests found that I had wrong**

1. **Deleting `assertCan` left every test green.** `heartbeat.send_own` is ✓ for
   every role, so the role never refuses — what refuses is the credential, and I
   had no `read_only` token in the suite. The gate was unguarded and the
   mutation is the only reason I know. *A permission test needs an actor for
   whom the permission actually differs* — LAI-081, LAI-405, and now here.
2. **A Viewer holding a token stored as `full` is still refused.** I expected
   that to pass. `can()` applies `effectiveTokenScope` at **check** time rather
   than trusting the stored row, so a token minted while somebody was a Member
   stops writing the moment they are demoted, with nothing revoking it. Stronger
   than what I was testing for, and now asserted as its own case.

**Discovered**
- **The `heartbeats.token_id` foreign key caught a fake fixture.** My service
  tests used a synthetic token id; the route tests mint real ones through the
  API and never met it. The constraint refused it immediately, which is the
  schema doing its job — a fabricated id would otherwise have sat in a test
  fixture claiming to be a token.
- **My branch is green this time, unlike LAI-408**, because the exemption entry
  went in from the start rather than after the fact. Verified it is
  load-bearing: removing it turns the drift test red.
- nothing filed.

## 2026-09-01T10:50:00Z — LAI-136

**Decisions**
- **A composite, not a `pretest` hook.** Both work; the composite is visible in
  `package.json` where somebody reads what `test` does. A `pretest` hook is
  invisible at the call site, and the whole defect here was a check that was not
  where people looked.
- **`test:watch` left alone**, so the fast inner loop is unchanged.
- **The web half is filed as LAI-141, not fixed here.** `server/web/package.json`
  is SHELL's (D-016, D-031) and this task's own Notes said to split rather than
  reach across. `node --test` strips types exactly as vitest does, so the hole is
  identical and the reason for the split is ownership alone.

slower. Cheap for a run that can no longer be green over a file that does not
