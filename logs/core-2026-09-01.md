  pair for a tool that no longer exists. A stale pair reads as coverage and is

**The mutation that taught me what this test actually guards**

My first attempt at AC6 mutated the **shared service** — `createTask` writing
`task.updated` instead of `task.created`. The `create_task` pair **stayed
green**, and something else went red.

That is the property working, and it took a minute to see: both sides call the
same service, so changing it moves them together. **Parity cannot be broken by
changing the thing both halves share** — which is exactly what the layering
rules guarantee, and exactly why CHIEF was right that this test *confirms* a
structural property rather than propping it up.

The mutation that matters is the **tool diverging from the route**. All three
name the tool:

```
× create_task — identical activity, differing only in attribution
× start_working — identical activity, differing only in attribution
× list_projects — identical activity, differing only in attribution
```

- `create_task` writing an extra comment the route does not → red.
- `start_working` reaching for `changeStatus` instead of `claimTask` → red.
  That one is the realistic failure: a plausible-looking substitution that
  produces a different verb.
- A read tool writing anything → red.
- A REST twin for `log_unlisted_work` appearing → the self-expiry fires and
  says to remove the entry.

**Discovered**
- **A mutation that goes red is not automatically a mutation that proved
  anything.** My first one went red on *"the agent's rows say agent"* — a
  different test entirely — and I would have recorded AC6 as satisfied had I
  only read the exit code. The harness prints the failing test name for exactly

- **My second mutation did not write anything.** I "made a read tool write" by

## 2026-09-01T16:45:00Z — LAI-118, append-only triggers survive a rebuild

**What changed**

**Decisions**

*The unconditional call is the mechanism, not `IF NOT EXISTS`.* A migration runs
once and cannot repair a database a later migration rebuilt.

*The post-condition checks the body, not the name — and this changed mid-task.*
My first version checked existence; mutating it away turned **nothing** red,
because `CREATE TRIGGER` either succeeds or throws, so the check was
unreachable. The reachable failure is a hand-pasted block that lost its `RAISE`:
present, correctly named, inert, and invisible to `IF NOT EXISTS` because
something holds the name.

*It throws rather than repairing.* A missing trigger is an accident of SQLite's
rebuild; a wrong one is a mistake in a migration, and rewriting it at boot hides
a file that will be applied again on the next clean install.

*AC6 needed no filing.* The criterion allows the migration folder, which is
`server/`.

**Discovered**

*My rebuild helper rebuilt nothing.* It renamed `` `activity` `` in the captured
DDL, but SQLite rewrites stored DDL in **double quotes** on
`ALTER TABLE … RENAME`, and every rebuild since 0000 has gone through one. The
replace matched nothing, and the test asserted on a table it had not touched. It
now matches either form and throws if the replacement did not land.

*The append-only assertions passed on an empty table.* A `BEFORE UPDATE` trigger
fires **per row**; with no rows the statement matches nothing and succeeds
whether or not the guarantee exists. Both of these are the harness lesson again:
the check ran, but not against what it named. Third and fourth instance today.

*Most of the file would pass if nothing ever called the function.* Only
`re-establishes the triggers on a boot with no pending migrations` fails when
the wiring is removed — and that is also the property that matters.
