**Decisions**

- One action for both reads, not two: they are one §3.1 row ("View own
  developer setup"), the own twin of `developer_setup.read_any`.
- A new action rather than `agent.read_own`: that one is held by tokens
  (`READ_ACTIONS`, pinned and agent tokens), and an agent's token must not
  read the pairing requests it could ask its person to approve.
- The list sits at the collection path of the existing resource
  (`/devices/pairing-requests`), where approve/deny already live; the
  activity under `/me/developer-setup/` where LAI-1156 can add more.
- "Pending" means exactly what the admin read means: open, claimed or
  approved, not expired. An **approved** request still waiting for the
  device to complete stays listed; denied, cancelled, completed and expired
  do not. The task's wording ("to approve or decline") would drop approved;
  kept the admin read's set so the two never disagree.
- The activity is built by calling `buildView` rather than re-assembling its
  inputs: one person's setup is cheap, and a second assembly path is how the
  two lists would drift.

**Discovered**

- `GET /devices/pairing-requests/:id` stays `agent.read_own`, so a token can
  still read one request it knows the id of. Not widened here; noted.
