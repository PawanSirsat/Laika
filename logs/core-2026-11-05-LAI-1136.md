**Decisions**
- `task_not_assignable` and `user_deactivated` are `details.reason` under
  `422 unprocessable`. §6.3's code list is closed, so they are not codes.
- **One answer for every way a first card does not qualify**, a missing id
  and another space's task included, so the error never confirms a task
  exists elsewhere. "Readable" comes down to "in this space": the adder holds
  `project.members.manage` there, so they can read every task in it.
- The assignment calls `updateTask` inside the outer transaction (a
  savepoint), not a copy of its logic. The import cycle
  projects → tasks → projects already existed through `offboarding.ts`.
- A blank message is stored as no message. The route trims it, and the
  service maps `''` to null.
- **§3.4 got a row (`system.notices.prune`)**, though the plan names only
  §3.1, §4.87, §6.4 and §11.6 for T3. The §11.6 prune it assigns needs a
  system action, and §3.4 is where every one is listed.
- Web client types `web/src/api/notices.ts` (named in the plan's T3 file
  list) were **not** written. The dispatch said server-only. They are
  LAI-1139's, and `NoticeView` sits in `UNPAIRED` until then.
- The `POST …/members` response is unchanged (`201 { members }`). The two
  request fields are optional, so no web mirror moved.
