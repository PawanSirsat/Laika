**Decisions**
- **Consumption lives in better-auth's sign-up hook, not in the accept route.**
  `POST /api/v1/auth/sign-up/email` is public and already took an `inviteToken`
  (D-004's gate reads it) — it validated the invite and consumed nothing, so the
  invitee landed on the default `member` role and the token stayed spendable for
  ever. An accept endpoint that consumed invites on its own would have been a
  polite door beside an open window. Rejected: doing it in the route and leaving
  the public path alone, which is what "build the accept endpoint" literally asks
  for and would have shipped the replay hole AC3 exists to close.
- **`user.invite` for create, list and revoke; plus `user.set_role` on create.**

  the actions list splits because that row names two operations. The second check
  is how `(not to Owner)` is enforced — rejected leaving it out, which lets an
  Admin mint an Owner account and makes the caveat on the direct role change
  decorative.
- **Revoke deletes the row.** Rejected adding `revoked_at`: §4.11 has no such
  column, so `schema.ts` would go ahead of the spec and LAI-051 would go red —
  the exact failure PM hit with §4.16 this week. A revoked pending invite is
  indistinguishable to every caller from one that never existed and nothing
  references it. An accepted invite answers 409 instead; that row is the record
  of how somebody got in.
- **Accept answers 403 where the preview answers 404**, both uniform across
  unknown / expired / spent. Accepting is an action the token has to authorise —
  and 403 is what the public sign-up path already answers for the same input, so
  the two cannot disagree. Rejected reusing `previewInvite` in the accept route,
  which is what I built first; it made a replay a 404 and split the two paths.
- **The service re-exports `ORG_ROLES` / `PROJECT_ROLES`** so the route can
  validate a role without importing `db/`. The house idiom (`routes/tasks.ts`,
  `routes/sprints.ts`) retypes the tuple in the route file — a fourth copy of a
  closed vocabulary that nothing checks against `db/enums.ts`. Rejected adding a
  fifth. Filed LAI-119 to converge the other two rather than leaving two idioms.
- **7 days, stated in the code with its reasoning.** Matches §4.12's meeting-review
  window, and §11.6 already sweeps both from one cron.
- **No `invite.created` / `invite.revoked` verbs.** §4.8 has none, AC7 asks only
  for `member.added`, and PM has asked that the missing-verb wart stop being filed.
  A decision, not an oversight.

## 2026-08-24T20:23:00Z — LAI-090

**What changed**
- server/src/auth/trusted-origins.ts — new. `localhost`, `127.0.0.1` and `::1`
  are one host when the configured URL is one of them; nothing else widens.
- server/src/http/auth-errors.ts — new. better-auth's failures translated into
  the §6.3 envelope, with a message naming the configured URL and the caller's.
- server/src/auth/auth.ts — uses the above; pins `disableOriginCheck: false`.
- server/src/app.ts — `/api/v1/auth/*` failures go through the translation;
  successes pass untouched.
- server/test/auth/{trusted-origins,origin}.test.ts,
  server/test/http/auth-errors.test.ts — new.

**Decisions**
- **Loopback spellings are one host.** The origin check is a CSRF defence: it
  stops a page on another *site* driving this API with the user's cookie. A page
  served from `http://127.0.0.1:3000` is served by this instance — nobody else
  can bind that port on that machine. Rejected the alternative of leaving them
  distinct: it stops no attacker and locked the owner out of their own instance
  with a message pointing at their password.
- **Deliberately not widened** to LAN addresses, hostnames or proxy origins, and
  it adds nothing when the configured URL is a real hostname. AC3 warned against
  the blanket fix and there is a probe that proves the narrow version is what
  shipped.
- **Translate at the mount point, not in the client.** The alternative was to fix
  the message in `api/auth.ts`, which is (a) Builder-B's and (b) the wrong layer
  — a second error shape on one prefix is a second thing every client has to
  know. Successes pass through untouched because better-auth's session payload
  and `Set-Cookie` are not ours to rewrite.
- **The message names both addresses.** An operator who can see the mismatch
  fixes it in seconds; one told only "invalid origin" has to guess which of the
  two the server thinks is wrong. Echoing the caller's own `Origin` back to that
  same caller adds no exposure — they sent it.
- **`details.message` repeats the envelope's message**, because `api/auth.ts`
  reads `details.message` and I may not edit it. Documented as transitional and
  filed as LAI-125, with a note that both halves must land together.

**Discovered**
- **better-auth disables its origin check under `NODE_ENV=test`** —
  `skipOriginCheck: … : isTest() ? true : false` in
  `dist/context/create-context.mjs:210`. The suite has therefore run with a
  weaker security posture than production, and **no test at any level could have
  caught this bug**: every request was accepted regardless of `Origin`. Found
  because my acceptance test returned 200 for `https://evil.example` and I could
  not explain it. Now pinned to `false` explicitly. This is the finding I would
  want reviewed hardest — a guard that cannot fail in the test environment is a
  guard nobody can regression-test.
- **I first blamed the socket.** The Hono test client returned 200 where the
