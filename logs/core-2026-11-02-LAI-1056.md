**Decisions**
- **Redeem calls `can()` on the owner rather than claiming D-124.** It mints
  a credential, which D-124's condition 1 forbids. The owner is loaded at
  redeem and asked about `agent.manage_own`; a deactivated owner gets a
  uniform 404. The device signature is the authentication. §6.1 needs a
  CHIEF paragraph for that, as plan §E.1 already says.
- **The challenge is stored on the exchange and returned on an unsigned
  redeem.** It is not a secret, and returning it rotates nothing, so a racer
  who knows the id cannot invalidate the device's challenge. Five bad
  signatures cancel the exchange, as pairing does.
- **Reconnect revokes every live token of the agent** in the redeem
  transaction. The new token carries the newest old one's scope and pin,
  never wider.
- **The status word is not computed on the server.** The verification route
  returns checks plus `now` and `last_seen_at`. "Session hooks unsupported"
  lives in the web's capability table (plan §E.6).
- **No `grants` on add tool:** least privilege. Grants go through the
  existing routes.

**Discovered**
- Omnigent and Hermes send `clientInfo.name = "mcp"`, so `tool_request` can
  never pass for them. Plan §M assumes it can. This is noted for CHIEF and
  not filed: it needs a decision on what counts as evidence.
- `GET /api/v1/me` answers no `agent` field for an agent token; the test
  reads `tokens.agent_id` instead. This was not investigated further.
