## 2026-11-18T23:10:02Z — LAI-1351 (round 3: review-407's should-fixes, the §4.4 pair)

**What changed**
- cli/src/attach.ts:
  - Every cleanup `DELETE` is checked. `--json` names the deleted uploads
    (`cleaned_up`) and the ones that failed (`cleanup_failed`). A failure is
    said loudly and the exit code stays non-zero.
  - The read-back `GET` is tried twice. If neither read answers, the attach
    is reported as linked but unverified: a warning, exit 0 and
    `verified: false`. It is never undone. Only a read that answers and shows
    a file missing removes the comment and the uploads.
- cli/src/office-text.ts — linear in the XML:
  - Elements are found with `indexOf` (opening tag, its `>`, its close), and
    the Word tokenizer is a tag-at-a-time `indexOf` loop. The lazy
    `[\s\S]*?</row>` and `[^>]*?` scans were quadratic on unclosed tags.
    Measured on the old patterns: 20k unclosed `<row>` took 262 ms and 20k
    unclosed `<w:p ` took 1.2 s, rising quadratically.
  - An unclosed element makes the file unreadable, so the attach is refused
    instead of the scan stopping, which would leave what follows unread.
  - `&#x110000;` makes the file unreadable instead of throwing.
  - A total of 128 MiB is inflated across all parts, beside the 64 MiB per
    part.
  - Prefixed SpreadsheetML (`<x:row>`) and any prefix for WordprocessingML are
    read.
- Tests:
  - cli/test/secret-scan.test.ts — seven crafted 2 MiB parts, each under
    750 ms and all under 1.5 s; an unclosed row hiding a token; a bad
    reference; a prefixed sheet; the total budget (39 cases).
  - cli/test/attach-e2e.test.ts — the all-or-none case checks each upload's
    `DELETE` answered 204 in the board's own log. New cases cover a read-back
    that fails twice (exit 0, nothing deleted) and no `Authorization` header
    on the store `PUT` (10 cases).

## 2026-11-18T23:38:00Z — LAI-1351 (round 4: review-407's residual)

**What changed**
- cli/src/office-text.ts:
  - **The text budget.** The 128 MiB budget is now spent by the text read
    out, not only by the XML inflated. The two amplifications the review
    found:
    - one 1 MiB shared string referenced by 600 cells, which threw
      `RangeError: Invalid string length`;
    - 20k rows with a cell at column ZZZ, which took 3.1 s and 445 MB.

    Both multiply small XML into huge text. A sheet is now read as cell
    references and column numbers, each cell and each tab of padding spent
    first, and its text is built only once the whole sheet fits. Word parts
    spend as they go.
  - **Any error is unreadable.** The reader now catches every error, not only
    unreadable XML: it is refused, with `--json` saying so.
  - The budget is a field, not a parameter property, because Node's type
    stripping refuses those (a known trap).
- Tests:
  - cli/test/secret-scan.test.ts (42 cases): both crafted cases come back
    unreadable, in 2.7 ms and 11 ms, with less than 128 MiB of heap growth,
    against a 1 s limit. A real sheet of the same shapes is still read. The
    total-budget case was adjusted for the text it now counts.
  - cli/test/attach-e2e.test.ts (11 cases): `&#x110000;` in a docx gives
    exit 1 and `--json` `{ ok: false, linked: false }` with "could not be
    opened to check it for secrets". No request reaches the board.

**Decisions**
- A sheet is built only after it fits, rather than capped while building.
  Spending before building means a crafted file costs no more memory than its
  references, so the refusal is cheap as well as correct.
