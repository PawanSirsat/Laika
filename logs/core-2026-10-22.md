**Decisions**
- Guarded on `org.read`, not `member_list.read`. Every role holds it, it is in
  `READ_ACTIONS`, so a read-only token reaches it, and it is not session-only.
  Who may do what is a fact about the organisation. `member_list.read` would
  answer alike today but is about people, which is LAI-222's argument against
  borrowing rows.
- Conditions are declared, each with a resource on which it holds and one on
  which it fails. A role that answers differently on the two is reported
  `conditional`; the alternative was a flat yes/no from the empty resource,
  which is the guess the task forbids. The eight cases: `user.set_role` (not
  to Owner), `project.join_public` (public only), `token.read_own` and
  `token.revoke_own` (own tokens), `profile.rate` (not themselves),
  `comment.edit` and `comment.delete` (own comments, for a member), and
  `task.delete` (tasks they created, for a member). A test probes every
  undeclared action across every resource shape `can.ts` reads, and fails if
  any of them depends on the resource.
- Project roles are evaluated as an org `member` holding each project role.
  That is the only org role whose project role is neither implied
  (owner/admin) nor capped (viewer).
- `me.actions` holds org actions only, conditional ones included. Project
  actions are listed per membership under `me.projects`, through
  `effectiveProjectRole`, so an org viewer's `lead` row reads `viewer`.
  `me.implicit_project_role` is `lead` for owner/admin, who hold it on
  projects with no membership row. The task's `me: { org_role, actions }`
  is kept and widened rather than mixing two scopes in one list.
- `task.write` and `project.settings.edit` are each granted by two §3.2 rows.
  Each label is the row naming the action's main use.
