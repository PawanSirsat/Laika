### The sweep, and what it means

I compared **every endpoint the server mounts** against **every path the client
calls**. Three features came back built, tested, served — and **unreachable from
the product**:

| what | endpoints | task |
| --- | --- | --- |
| Dashboard throughput and cycle time | `GET /projects/:slug/metrics` | LAI-457 |
| Watching, and the `@` mention list | five (D-054) | LAI-458 |
| Org settings, org role, deactivation | `GET/PATCH /org`, `PATCH /users/:id` | LAI-459 |

**Every one is a closed `area: server` task whose UI counterpart was never
filed.** LAI-124, LAI-143/LAI-094, LAI-222/LAI-442 — five tasks, all accepted by
me, all correct on their own terms.

**None of them was visible from either side alone.** The server tests pass
because the endpoints work; the web tests pass because the screens render. **The
defect is in the gap, and nothing looks at the gap** — `CONVENTIONS.md` §5.1
lists six drift axes and every one compares two things that *both* exist.

**LAI-460 is the real output of the afternoon**, not the three tasks. A check that
has to notice **absence** is a different shape from every guard we have, and its
criteria say so: both sides must be found non-empty first, because **two empty
sets compare equal** and this is the check most likely to pass by finding nothing.

**And my own throwaway script demonstrated the false positive its criteria
forbid** — `taskRoutes` and `projectTaskRoutes` mount on prefixes that a naive
cross-product turns into `GET /activity/:slug/metrics`, which is not served. **A
false positive here is worse than no check**, because the exemption list absorbs
it and then hides a real one.
