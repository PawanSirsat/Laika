**Decisions**
- Brotli quality 9, not 11 — measured on the real bundle: q11 1.6 s on an M4
  for 166.6 KB, q9 58 ms for 179.3 KB. On a t4g.micro the first visitor after
  a deploy would wait for q11; 13 KB is not worth that.
- Compress on first request, not at startup — no new wiring in `index.ts`, and
  measured at 30 ms for the JS here. Concurrent first requests share one load.
- `ready` filter: batches rather than keeping the old full read — same rows in
  the same order, so the same answer, and bounded. Batch floor 50 so the
  64-task equivalence fixture actually crosses a batch boundary; a mutation
  that stops after the first batch goes red.
- Project feed index: unary `+` on `org_id` (and on `project_id` for a task
  feed) rather than `ANALYZE`/`PRAGMA optimize` — deterministic on an empty
  test database and on production alike, and asserted against the plan of
  the SQL the code really issues. Stats would make the plan depend on data.
- API compression measures the JSON first — `c.json` sets no Content-Length,
  so `hono/compress`'s threshold alone would gzip a 60-byte health check.
- Range is ignored on static files (a whole 200): legal, and avoids a 206
  counted against the wrong encoding.
