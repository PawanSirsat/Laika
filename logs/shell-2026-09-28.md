**Three things this found that the task did not predict**

1. **`whoami` could not see what `install.sh` writes.** The installer writes
   `~/.laika/env` and only that; `whoami` read `~/.claude/settings.json` and
   only that. Clean sandbox → successful install → `laika whoami` →
   *"This machine is not connected to a board."* From the command the
   installer's own closing line promises, and the first command the Connect
   screen offers a new developer. It now reads both **and prints which file
   answered**, which turns D-046's two-locations problem from invisible into
   diagnosable. It does not settle D-046 — that is CHIEF's.

2. **The clobber guard did not guard.** `[ "$EXISTING" != "$BIN/laika" ]` was
   there to spare our own link on a re-run, but `[ ! -L ]` already does that.
   All the extra clause ever did was excuse **a real file somebody else put at
   the exact path we install to** — the one case worth guarding. The sandbox
   overwrote one and the installer printed `✓`.

   Per CLAUDE.md §5's sampling rule I swept both `ln -sf` sites rather than
   patching the one the test found. `laika-claude` had **no** guard at all; it
   has the same one now. The rule earned its place again: I would have fixed
   the found one and shipped the other.

3. **The test file deadlocked, and the symptom named no test.**
   `# pass 0  # fail 0` with the *file* timing out. The stub board runs in the
   test process; the CLI was invoked with `execFileSync`, which blocks the
   event loop — so the server could never accept the connection the child was
   waiting on, and the reporter's output was stuck behind the same blocked loop,
   which is why not one of ten tests could say what it did.

   **Worth remembering because it reads as a broken runner, not a broken test.**
   I spent two rounds rewriting the helper before measuring: running only the
   describe block with no server reported `1 pass, 1 fail` immediately, which
   located it in one command. Fixed with a promisified `execFile`.

## 00:05 +05:30 — LAI-623, a fourth finding: the sandbox was cleaner than reality

After moving the task to review I ran the command **for real** rather than only
in the sandbox. All ten tests were green. The real run:

```
$ ./cli/bin/laika whoami
laika: unknown command "whoami"
  npx laika init     authenticate, create a token, and save it
```

**Both defects the task exists to fix, answered by a `dist/` built five days
earlier.** The shim preferred `dist/index.js` whenever it was readable, and my
sandbox copied `bin/` and `src/` and no `dist/` — so the fixture omitted the
only thing that could break it.

This is the same family as "an assertion a broken setup satisfies", one level
up: **not a loose assertion, a fixture that cannot reach the failure.** Every
control I had mutation-verified was real; they were all measuring a code path
the real invocation does not take.

`dist/` is gitignored, so a fresh clone takes the src path and a new teammate
never hits it. Every machine that has ever run `pnpm -C cli build` does, for
ever, silently. The shim now takes `dist` only when no source file postdates it.
Three tests, including a control asserting a **fresh** `dist` is still used —
without that control, "always ignore dist" passes and I would have broken the
path a published package and an old Node both take. Both directions mutated:
unconditional-dist kills two, ignore-dist kills the control.

**The lesson I want to keep**: I verified the thing I built rather than the
thing people run. Running it for real took eight seconds and found what
thirteen tests and six mutations had not. Do that first next time, not after
moving to review.
