## 2026-08-31T07:20:24Z — LAI-045

**What changed**
- `server/src/db/activity.ts` — `apiFieldNames(table, keys)` translates a Drizzle
  property to its column's SQL name (the write side, inherited uncommitted from
  the previous CORE session); `sqlNameOf` factored out; `DRIZZLE_TO_API`, a
  schema-wide map; `apiPayload(row)`, the read side (AC3)
- `server/src/services/tasks.ts`, `.../projects.ts` — the two `Object.keys(changes)`
  payloads now translate
- `server/src/services/events.ts` — `eventView` serves `apiPayload`, not `readPayload`
- `server/test/tooling/activity-payload-names.test.ts` — the guard, rewritten and
  widened: derived forbidden list, ambiguity check, full-sweep coverage guard, AC3
- `server/test/db/activity.test.ts` — the exact-exports list gains the two new names
- `server/test/services/tasks.test.ts` — one assertion that pinned the old spelling

**Decisions**
- **Translate on read, at `eventView`, rather than accepting both spellings.**
  AC3 allowed either. `activity` is append-only, so fixing only the write side
  leaves the audit trail speaking two vocabularies split by date — the same
  defect, reshaped, and harder to spot because each row is individually
  defensible. `eventView` is the single boundary every client crosses (SSE via
  `routes/events.ts`, REST via `services/activity.ts`), so one call covers every
  consumer including MCP, which does not exist yet.
- **The stored row is not rewritten and `readPayload` stays verbatim.**
  Normalising a field's *name* does not alter the audited fact, but an audit log
  should still be able to show exactly what was written. Two functions, and the
  boundary between them is the concept.
- **Only entries of a `changed` array are translated.** Camel-case could only
  ever reach a payload through the two sites that built one from
  `Object.keys(changes)`, and both wrote into `changed`. Translating every string
  in a payload would be broader and worse: payloads carry user-supplied values, a
  project may legally be called `startsOn`, and rewriting one would corrupt an
  audit row to fix a name that was never wrong.
- **Schema-wide map on the read side, table-scoped on the write side.** A stored
  row does not say which Drizzle object produced it. Sound only while no property
  means two different columns — measured (70 properties, 0 conflicts) and then
  asserted in the test rather than left as today's measurement.
- Rejected splitting this into a separate follow-up task for the read side. AC3
  is a criterion of *this* task; leaving it would have meant ticking a box the
  work had not earned.

**The audit AC2 asked for — every mutating path**

22 `appendActivity` call sites across six service files. Exactly **two** ever
carried a Drizzle property, and both are the `Object.keys(changes)` shape:

| file | sites | offenders |
| --- | --- | --- |
| `services/tasks.ts` | 7 | `updateTask`'s non-reassign branch |
| `services/projects.ts` | 6 | `updateProject` |
| `services/comments.ts` | 3 | none — `{ action, comment_id }` |
| `services/sprints.ts` | 2 | none |
| `services/setup.ts` | 2 | none |
| `services/invites.ts` | 2 | none |

Two that looked like offenders and are not:

- `services/sprints.ts` `recordSprintChange` spreads `...rest` into its payload,
  which carries a `changed?: string[]`. Its entries are hand-written in
  `updateSprint` — `name`, `goal`, `dates`, `status` — never `Object.keys`.
- `invites.ts` writes `invited_by`, which is not the column name (`created_by`).
  A deliberate descriptive name, already `snake_case`. Left alone.

One thing I checked and deliberately did **not** change: `updateSprint` records
`changed: ['dates']`, and `dates` names no §6.3 field — it summarises `starts_on`
and `ends_on`, which the code also tests as one condition. It is not a Drizzle
name, so it is outside this task, and renaming it would change an audit
vocabulary on a guess about what a reader prefers. Noting it rather than
silently widening scope.

**Nothing reads these names today.** The only client consumer of a payload is
`server/web/src/api/activity.ts`, which reads `from`/`to` on
`task.status_changed` and nothing else. So no UI could have rendered blank — but
that is a fact about today's UI, not a property of the fix, which is why the
translation is at the boundary rather than left undone.

**Every guard was proved able to fail.** Six mutations, each red:
reverting `tasks.ts`; reverting `projects.ts`; making the read-side translation a
no-op; `eventView` serving raw payloads; dropping the comment paths from the
sweep; and adding an emitter of an uncovered type to a service. The last is the
one that matters — it proves `emittedActivityTypes()` genuinely reads the service
source, so when M3 adds `token.created` this guard demands coverage instead of
quietly covering less than it claims.

**Discovered**
- The sweep I inherited exercised **4 of 22 paths** while asserting "no mutating
  path writes a Drizzle property". It was green and it was overclaiming. The fix
  was not more paths but a *coverage assertion that expires*: derive the emitted
  type set from the service source and fail when the sweep misses one. A test
  whose coverage is asserted rather than assumed is the difference between this
  and the six times this repo has been bitten by a justification that went stale
  (LAI-052, LAI-080, LAI-043, LAI-066, LAI-211, LAI-213).
- `pnpm typecheck` and `vitest` disagree, and vitest is the weaker one. Three
  real type errors in my test file ran green under vitest, which transpiles
  without checking. `tsc` caught them. **A green test run is not a typechecked
  one**, and the order that catches this is test → typecheck → lint → format,
  never test alone.
- `build.test.ts` catches what `typecheck` does not: a `table as Record<string, unknown>`
  cast passed `tsconfig.json` but failed `tsconfig.build.json`. Worth knowing that
  the build is a genuinely separate gate, not a slower copy of typecheck.
- `blocked` is not a task status. It is derived from `ready`, and the §5
  transition table has no such state — a detail easy to get wrong from the board's
  column names alone.
- nothing filed.

## 2026-08-31T07:45:12Z — LAI-414

**What changed**
- `server/test/tooling/activity-payload-names.test.ts` — `sourceFiles()` walks
  `server/src` and the sweep scans what it finds; the hand-written six-file list
  is gone; extraction is no longer line-anchored; two new tests assert discovery
  is neither empty nor pointed at the wrong place

**Decisions**
- **Walk all of `server/src`, not just `services/`.** AC1 allowed either
  directory-reading or deriving from what imports `appendActivity`. Reading the
  whole source tree also covers an emitter added under `http/routes/` or in the
  `mcp/` directory LAI-406 creates. Today every call site is in `services/`; the
  guard should not need editing for that to stop being true.
- **No exclusion list, because nothing needs excluding.** AC4 required any
  exclusion to be named, reasoned and self-expiring. Widening to all thirteen
  service files — and in fact to all of `src/` — turned up no emitter the sweep
  was not already producing, so there is nothing to exclude and no mechanism to
  rot. `db/activity.ts` is scanned and contributes nothing: it *defines*
  `appendActivity`, and a definition names no type.
- File names still appear in the file, but as **assertions that discovery
  reaches them** (`expect(found).toContain('services/users.ts')`), never as the
  list being scanned. That is the opposite of the defect: it fails if discovery
  stops finding a file, where the old list failed to look.

**The proof AC2 asked for**

An emitter of `token.created` added to `services/users.ts` — a file the old six
never named, and the case that was green when this task was filed:

```
AssertionError: services emit these types and this sweep never produced one:
expected [ 'token.created' ] to deeply equal []
```

Red in both wrappings, multi-line and single-line. Probe reverted; `users.ts` is
byte-identical to HEAD.

**Discovered**

Two defects in my own first attempt at this fix, both found by measuring rather
than reasoning, and both the same family as the bug being fixed:

- **The extractor was line-anchored.** It matched `/^\s*type:/`, so it only saw a
  `type:` that began a line. A single-line `appendActivity(...)` call in
  `users.ts` left the guard **green**. I caught it only because I re-ran the
  probe after changing an unrelated assertion and the wrapping happened to
  differ. A coverage check tied to how source is wrapped is under-coverage with
  extra steps. It now reads §4.8 literals anywhere in the call block; the cost is
  that a payload *value* which is itself an activity type would read as an
  emission — nothing writes one, and that failure would be loud where the one it
  replaces was silent.
- **My own sanity assertion would have fired on correct work.** I wrote
  `expect(emitted).not.toContain('token.created')` to prove the extractor was not
  inventing types. True today — and **LAI-402 makes it false by doing exactly
  what it is supposed to do.** The next builder would have met a red test on
  correct code and deleted the assertion. Replaced with a property that cannot
  expire: everything found is a member of `ACTIVITY_TYPES`. *A guard that fires
  on correct code is a bug in the guard; precision is the fix, not deletion.*
- **The generalisation that caused LAI-414 in the first place was mine.** I
  proved LAI-045's coverage guard red by adding an emitter to `tasks.ts` — a file
  on the list — and then told CHIEF it would catch `services/tokens.ts`, which is
  not. The measurement was real and the conclusion did not follow from it.
  **Where a guard is proved to fire matters as much as that it fires**: the probe
  has to sit where the *next* change will land, not where the code already is.
- nothing filed.

**State**

`started:` removed) so this could go first — CHIEF's sequencing, and I agree with
it: a guard repaired after `services/tokens.ts` lands is a guard that was never

## 2026-08-31T08:35:00Z — LAI-402

**What changed**
- `server/src/auth/tokens.ts` (new) — `newTokenSecret`, `hashToken`,
  `tokenDisplayPrefix`
- `server/src/services/tokens.ts` (new) — mint, list own, list any, revoke own,
  revoke any; every rule lives here
- `server/src/http/routes/tokens.ts` (new) — `tokenRoutes`, `userTokenRoutes`
- `server/src/app.ts` — mounts both, `userTokenRoutes` before `userRoutes`
- `server/test/auth/tokens.test.ts`, `server/test/services/tokens.test.ts`,
  `server/test/http/routes/tokens.test.ts` (new) — 49 tests
- `server/test/tooling/activity-payload-names.test.ts` — sweep now exercises
  `token.created` / `token.revoked`

**Decisions**
- **`auth/tokens.ts` split from the service**, mirroring `auth/invites.ts` /
  `services/invites.ts`. LAI-403's middleware needs `hashToken` to recognise a
  presented credential and has no business importing the CRUD surface to get it.
- **Rejection sampling, with an injectable random source.** 256 is not a
  multiple of 62, so `randomBytes % 62` makes the alphabet's first eight
  characters ~25% likelier. The injection exists because **rejection cannot be
  proved statistically at any sample size this suite can afford**: the bias
  moves a bucket from ~129 to ~161 in 8,000 characters, which no non-flaky bound
  separates from noise. Feeding byte 250 and asserting the *next* byte decides
  is deterministic and exact.
- **Scope forced, not refused.** §3.1's cell reads "Generate own tokens ✓
  (`read_only` forced)". Forcing is the literal reading; a `400` would be
  inventing a refusal the spec does not describe. Uses `forcedTokenScope`, which
  `can()` also calls, so creation and enforcement cannot disagree.
- **Existence checked as well as permission** on scoped project ids. An Owner
  has implicit lead everywhere, so `canSeeProject` says yes to an id that names
  no project at all — a token scoped to a phantom, created without complaint.
  Found by reasoning about the policy and then written as a test that fails
  without the existence check.
- **Revoking twice writes no second activity row.** §6.4's DELETE is idempotent
  so the status is 204 either way, but nothing changed on the second call. This
  codebase already refuses a no-op status transition because it "would write an
  `activity` row claiming a change happened"; same rule, same reason.
- **The admin revoke path checks the token belongs to the user in the URL.**
  Without it an admin could revoke anybody's token through anybody's path and
  the audit row would name the wrong owner. 404, not 403 — the token does not
  exist *at that path*.
- **`prefix` is the first 8 characters of the whole token**, so `lai_` plus
  four. That is §4.9 read literally. Four distinguishing characters is ample for
  the handful of tokens one person holds, which is what the field is for, and it
  is not used as a lookup key. Noting it because a reader may expect eight
  random characters.
- **Paginated like every other list**, though one person's tokens are few:
  `buildPage` emits a `next_cursor`, and returning one the service cannot honour
  would be a contract that lies. Keyset copied from `listInvites`.

**Verified against a running instance, not only the test client**
- The plaintext appears in **no database file, including the `-wal`** — which is
  where uncommitted pages live and where a naive check would miss it.
- Not in `GET /tokens`, and no 64-hex hash either.
- Not in the server's own log. CHIEF flagged that `logger.ts` emits `token_id`;
  it never sees a body, and no token secret is in a path, so there is no route
  by which it could. Checked rather than reasoned.
- Revoke → 204, revoke again → 204, anonymous → 401.
- Exactly one `token.created` and one `token.revoked`, both `project_id IS NULL`,
  both `actor_kind: user`, both payloads `snake_case`.

**Discovered**
- **`LIMITS.token` is declared and unreachable.** `classify(path, actorId)` has
  no token identity to key on, and LAI-403's criteria cover `actor_kind`,
  `token_id` and `last_used_at` but say nothing about rate limiting — so once
  tokens can authenticate, an agent would spend the 600/min *session* budget
  rather than its own 120/min. Falls between the two tasks rather than inside
  either. → **LAI-138 filed** (discovered-from: LAI-402, depends-on: LAI-403).
  LAI-402's Notes said to wire it if trivial and file if not; it is not.
- **The LAI-414 guard fired on this work, and was right.** Emitting
  `token.created` made the coverage assertion demand the sweep exercise it.
  That is D-037's case exactly: a red test met while building something new is
  not automatically a defect in the new work. Read it, saw it was the guard
  doing its job, extended the sweep. Had I written the brittle version of that
  assertion — `expect(emitted).not.toContain('token.created')`, which I nearly
  shipped in LAI-414 — I would have met a red test on correct code today and
  been tempted to delete a real guard.
- **`structure.test.ts` also fired**, wanting a mirrored test per new src
  module. Also right, also not a defect.
- **A test of mine passed while proving nothing, and said so loudly.**
  `mint(body, undefined)` falls through to the cookie parameter's *default*, so
  the "refuses an anonymous caller" case was authenticated as the Owner. It
  failed 201-vs-401 rather than passing quietly — only because the assertion was
  a status code that could not be satisfied by the wrong request.
- **I nearly ran my verification against another session's server.** `PORT=3370`
  failed `EADDRINUSE` and exited 1 — but `GET /health` still answered 200,
  because SHELL holds that port now. `uptime_ms: 1115605` was the tell: eighteen
  minutes, on a process I had started one second earlier. **A health check
  answering does not mean your server is answering.** Moved to 3373 and
  confirmed uptime 6.5s before trusting a single result. Their process was left
  alone.
- **zsh word-splitting, again.** `J='-H a -H b'; curl $J ...` passes one
  argument, not four; setup came back 400 and the endpoint was fine. Second time
  this exact trap has cost me a wrong conclusion.
