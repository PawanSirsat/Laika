**Decisions**
- **Translate on read, at `eventView`, rather than accepting both spellings.**
  AC3 allowed either. `activity` is append-only, so fixing only the write side
  leaves the audit trail speaking two vocabularies split by date — the same
  defect, reshaped, and harder to spot because each row is individually
  defensible. `eventView` is the single boundary every client crosses (SSE via

  consumer including MCP, which does not exist yet.
- **The stored row is not rewritten and `readPayload` stays verbatim.**
  Normalising a field's *name* does not alter the audited fact, but an audit log
  should still be able to show exactly what was written. Two functions, and the
  boundary between them is the concept.
- **Only entries of a `changed` array are translated.** Camel-case could only
  ever reach a payload through the two sites that built one from
  `Object.keys(changes)`, and both wrote into `changed`. Translating every string
  in a payload would be broader and worse: payloads carry user-supplied values, a
  project may legally be called `startsOn`, and rewriting one would corrupt an
  audit row to fix a name that was never wrong.
- **Schema-wide map on the read side, table-scoped on the write side.** A stored
  row does not say which Drizzle object produced it. Sound only while no property
  means two different columns — measured (70 properties, 0 conflicts) and then
  asserted in the test rather than left as today's measurement.
- Rejected splitting this into a separate follow-up task for the read side. AC3
  is a criterion of *this* task; leaving it would have meant ticking a box the
  work had not earned.

- **The admin revoke path checks the token belongs to the user in the URL.**

  exist *at that path*.

## 2026-08-31T09:15:00Z — LAI-403

**What changed**

- `server/src/auth/tokens.ts` — `findTokenBySecret`, `touchTokenUsage`,

- `server/src/http/middleware/logger.ts` — real `actor_kind` / `token_id`
- `server/src/services/{tasks,projects,comments,sprints,tokens}.ts` — 18 call

- `server/test/http/middleware/auth.test.ts` (new, 17 tests),
  `server/test/auth/tokens.test.ts` (+12), plus `TokenContext` literals in
  `can.test.ts` and `comments.test.ts`

**Decisions**
- **The token wins when both a token and a cookie are present**, and a bad token
  is a 401 rather than a fall-through. Two arguments, same direction: *explicit
  beats ambient* — a browser attaches its cookie unasked, an `Authorization`
  header is deliberate — and *narrower beats wider*, since a token carries a
  scope and possibly a project whitelist where a session carries full authority.
  Cookie-wins would let an agent that happens to hold a session escape the limits
  of the token it presented, which is the one direction this must never go. The
  no-fallback rule follows from the same argument: falling back would let an
  expired or revoked token silently act with the session's full authority.
- **The rejection reason is a field on `TokenAuthError`, not in `details`.**
  I wrote it into `details` first, with a comment claiming `details` is not
  serialised for `unauthorized`. **Then I checked `toBody()` and it is.** Had I
  trusted the comment I would have shipped an endpoint telling an
  unauthenticated caller whether a token is unknown or merely revoked — which
  distinguishes "this never existed" from "this existed", free information about
  somebody else's token.
- **An unreadable `project_ids_json` becomes an empty whitelist, never `null`.**
  `null` means "every project the user can reach", so a parse failure would
  *widen* a scoped token to an unscoped one. Only one direction of that failure
  is safe and it is not the convenient one.
- **`timingSafeEqual` after an indexed lookup**, which looks redundant. It is
  not quite: the lookup proves SQLite found a row for this hash, the compare
  proves the hash is that row's. One fixed-length compare on a path that already
  hit the disk.
- **Throttle: 60s**, as the criterion invited me to choose. A token is read on
  **every** request, so an unthrottled stamp turns `GET /tasks` into a write,
  takes the write lock, and puts an agent's read traffic in contention with the
  board's actual work. A minute is enough resolution for a screen showing a date
  and collapses a thousand requests into one write.
- **One `activityActor` helper rather than three lines at eighteen sites.** The
  fields move together, so spreading one object means a new call site cannot
  record a cookie's attribution for an agent's request by forgetting a field.
  `setup.ts` and `consumeInvite` keep their literals: a first-boot owner and a
  brand-new signup have no `ResolvedActor` and are cookie paths by construction.

**The origin question — settled, and no `docs` task needed**

CHIEF asked me to write down what I concluded and file against `docs` if the
spec needed to say something it does not. **It already says it**, §6.1:

> **`/api/v1/auth/*` is origin-checked; nothing else is.** The REST endpoints and
> the SSE stream (§11.5) rely on the `SameSite=Lax` cookie instead.

An agent never touches `/auth/*` — it presents a token on `/api/v1/*` and later
`/mcp`, neither of which is origin-checked, and it has no browser to send an
`Origin` from. There is no undocumented exception and no hole for `/mcp` to fall
through; the rule the rest of the API keeps is a rule about `/auth/*` only.

So: **nothing filed.** Filing a docs task to restate a sentence the spec already
contains would be noise, and I would rather say I checked and found it covered.

Two tests pin it anyway, because the *reason* it works is one sentence a future
CORS change could invalidate, and that failure would land on every agent at once.

**Verified live, on port 3376** (checked free first; `uptime_ms: 11758`
confirmed it was mine before I trusted anything — CLAUDE.md §4.3)
- Under **`NODE_ENV=production`**, which matters: the suite runs under
  `NODE_ENV=test`, where better-auth's origin check is **off**. A test alone
  could not have shown the no-`Origin` case works where it counts.
- No `Origin` header at all: `read_only` GET 200, `read_only` POST **403**,
  `full` POST 201, unknown token 401, bad token + good cookie **401**.
- `activity`: `project.created` by cookie → `user`, null token; by token →
  `agent` with the real token id, same `actor_id` both times.
- `last_used_at` unchanged across five further requests.
- Request log carries `actor_kind: agent` and a real `token_id`; a rejected
  token logs `reason: unknown` while the 401 body carries `details: null`.

**Discovered**
- **`ApiError.toBody()` serialises `details`.** I asserted the opposite in a
  comment and was wrong. The lesson is narrow and worth keeping: *a comment
  explaining why something is safe is the thing most worth checking, because it
  is what stops the next reader checking.*
- **`NODE_ENV=test` hides the origin check**, so anything about origins is
  invisible to the suite by construction. Same blind spot as better-auth's rate
  limiting. Live verification under `production` is not belt-and-braces here; it
  is the only way to see it.
- nothing filed.

**The lint rule was proved red before I trusted it (AC1)**

CHIEF's condition, and it mattered: the `no-restricted-imports` block targets
`server/src/mcp/**/*.ts`, and **that directory did not exist**, so the rule had
never matched a single file. A pattern aimed at nothing passes silently.

I created the directory, added a file importing `db/schema.ts` and
`http/routes/health.ts`, and watched `pnpm lint` fail with both violations named.
Then removed it. It is a live rule, not an aspirational one.

**Decisions**
- **Stateless transport**, and it is a security decision before a simplicity
  one. A stateful MCP session resolves the actor once at `initialize` and keeps
  serving it, so a token revoked mid-session goes on working until the client
  disconnects. LAI-403 re-derives the actor from the token on every request;
  statelessness is what keeps that true at `/mcp`.
- **`sessionIdGenerator` is omitted, not set to `undefined`.** Its absence is
  the stateless switch. Writing it explicitly does not compile under
  `exactOptionalPropertyTypes`, and an omitted key reads as an oversight — so
  the comment says out loud that the omission is the decision.
- **`enableJsonResponse: true`** — no SSE stream, so no in-flight request that
  never ends. That is what §11.5's activity feed needed `onStopping` for.
- **`WebStandardStreamableHTTPServerTransport`**, not the Node one: it takes a
  `Request` and returns a `Response`, which Hono already speaks, so nothing
  adapts between two HTTP models. The SDK's own docs show the Hono call.
- **No `can()` call in `routes/mcp.ts`, deliberately.** CLAUDE.md §5 requires
  one on every endpoint "including MCP paths", and I considered adding one.
  `/mcp` itself reads and writes nothing: it is a transport that dispatches to
  tools, each of which calls the service that calls `can()`. A `can()` here
