**Decisions**

- Folded `assign_task` into `update_task.assignee` rather than shipping a
  separate tool (AC4 left the call to me). `updateTask` already writes
  `task.assigned` when the assignee changes, so a second tool would be a second
  name for one service call, and every tool costs an agent context window.
- An assignee may be an id **or a project member's email**, resolved through
  `listMembers`. Rejected resolving against the org directory (`listUsers`):
  it sits behind `member_list.read`, which a project-scoped token need not have,
  and it would make assigning work to a non-member the easy path.
- Sprints are addressed by **id only**. Rejected accepting a name for
  `set_task_sprint` (where the task's project makes it unambiguous), because
  `update_sprint` takes no project and could not do the same — one parameter
  meaning two things across two tools is worse than one extra `list_sprints`.
- `sprintTaskCounts` is a new service function rather than bucketing
  `listTasks`. Every list service returns `limit + 1` rows, so the obvious
  version is silently short past the page size — and a wrong count does not
  announce itself.
- `update_project_context` requires `mode`. Rejected defaulting to `append`
  (safe but surprising) and to `replace` (destructive): there is no safe default
  between adding a paragraph and discarding a document.
- Tool fields are `description` / `acceptance`, not the AC's `description_md` /
  `acceptance_md`, and keep `create_task`'s existing tighter MCP length caps.
  Consistency inside the MCP surface beat consistency with the REST body, which
  this file already departs from.

**Discovered**

- **`2026-02-31` parses.** `Date.parse('2026-02-31T00:00:00.000Z')` returns the
  3rd of March rather than `NaN` — only `2026-13-01` fails outright. A regex
  plus a parse is not enough to validate a date; `toTimestamp` compares the date
  back out, and that round-trip is the only thing between an agent's typo and a
  sprint silently starting three days late.
- **There is no `due_date` column.** AC3 asked for it; `grep dueDate` over
  `server/src/db/schema.ts` returns nothing. Tasks carry `started_at` and
  `completed_at`, which are actuals — D-014 gives tasks no planned dates on
  purpose. Not invented, recorded in the task file as the one sub-feature of
  AC3 that did not ship. No task filed: adding it is a product decision for
  CHIEF, not a gap in this one.
- **The AC's sprint vocabulary was wrong twice** — `state?: planned|active|closed`
  against `SPRINT_STATUSES = ['planned', 'active', 'completed']` in
  `db/enums.ts:183`. Read the enum rather than the description of it.
- **A third owner appeared that AC7 did not predict**, the D-056 shape exactly:
  `cli/test/plugin-mcp.test.ts` spells the eleven tool names out and
  `plugin/README.md` says "eleven" twice. Both are SHELL's, and there is no
  entry CORE could take that is not a crossing. → LAI-176 filed
  (discovered-from: LAI-611).
- `pnpm -r` **bails on the first failing workspace**, so the root `pnpm test`
  stopped at `cli` before `server`'s vitest finished. The root exit code alone
