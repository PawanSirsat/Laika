**Decisions**
- `SOURCE_COMMIT` gets no §11.7 row of its own. That table's first column is the server's
  runtime contract, and `env-contract.test.ts` requires every row there to be read by
  `readEnv`. A row for a build-only arg would turn the server ↔ SPEC check red. It is named
  inside the `LAIKA_BUILD_COMMIT` row instead.
- The test asserts the order of the `ARG`s against the `ENV`, not only that they are present.
  A regex for presence alone stays green when `ARG SOURCE_COMMIT` sits below the `ENV`, and the
  build above shows that ordering silently bakes an empty commit.
- No full `--target runtime` build. It needs the whole install and both app builds on Belka
  under load, and the tiny builds already test Docker's handling of the exact lines.

**Discovered**
- Coolify's source (`app/Jobs/ApplicationDeploymentJob.php`, v4.x, read 2026-11-18): with
  "Include source commit in build" on, `SOURCE_COMMIT` is `$this->commit`. That is the webhook's
  sha, or for a manual deploy `HEAD` resolved through `git ls-remote` to a 40-hex sha. It stays
  the literal `HEAD` if that output cannot be parsed, and one code path puts `unknown` when the
  commit is null. `LAIKA_BUILD_COMMIT` must be 7–40 lowercase hex or the server refuses to start
  (§11.7), so either literal would stop the container from booting rather than report "unknown".
  Normal Coolify deploys never hit this. Raised with CHIEF instead of filed, since the right
  answer (filter in the entrypoint, or accept the risk) is a design call.
- A `LAIKA_BUILD_COMMIT` left in Coolify as a build variable would still win over
  `SOURCE_COMMIT`, and as a runtime variable it overrides the image. The card already says CHIEF
  deletes it after this lands.
