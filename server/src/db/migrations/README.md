# Migrations

Generated by `pnpm run db:generate` from `../schema.ts`. Forward-only (SPEC
§11.3), applied at boot by `runMigrations` in `../migrate.ts`.

Applied migrations are **history**. Do not edit one that has shipped — drizzle
records each file's hash, and changing a file changes what a migrated database
disagrees with.

## You no longer need to paste the append-only triggers (LAI-118)

`activity` is append-only (§4.8), enforced by two SQLite triggers. Any change to
that table makes `drizzle-kit` rebuild it — create the new shape, copy, drop,
rename — and **SQLite drops a table's triggers with the table**. `drizzle-kit`
does not know they exist, so it does not put them back.

Migrations `0003`, `0004`, `0005` and `0008` each carry a hand-pasted
`CREATE TRIGGER` block for exactly this reason. **They stay** — they are history,
and a database migrated by them took the block from there.

**New migrations do not need one.** `runMigrations` calls
`ensureActivityTriggers` after every migration pass, on every boot, and it
verifies the triggers *abort* rather than merely exist. Read that function before
adding a block anyway: it explains why `CREATE TRIGGER IF NOT EXISTS` inside a
migration is not the same mechanism, and why a name check is not enough.

Pasting one regardless is harmless, just redundant.

## Two things a change to `activity` still has to think about

- **`rowid` must not be renumbered.** The SSE stream (§11.5) and the activity
  feed use it as their monotonic cursor. `test/db/activity.test.ts` asserts a
  rebuild preserves it (LAI-110).
- **The verb vocabulary is a `CHECK` constraint**, so growing it is a rebuild,
  which is what makes the point above recur.
